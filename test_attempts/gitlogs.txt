    Fix maple tree VMA walker using correct kernel node type detection
    
    The previous implementation was treating internal nodes as leaves and following
    garbage pointers, leading to invalid VMAs like vm_start=0x5. This fixes the
    core issues:
    
    1. **Correct node type detection**: Use kernel's exact method (ptr >> 3) & 0x0F
       instead of complex bit manipulation and heuristics
    
    2. **Proper leaf identification**: Only treat types 0,1 as leaves containing VMAs,
       types 2,3 are internal nodes containing child pointers
    
    3. **Remove follow-everything logic**: Stop treating failed VMA reads as potential
       child pointers - leaf nodes contain VMAs, not more child nodes
    
    4. **Fix VMA validation**: Accept ARM64 user space addresses up to 48-bit limit
       (0x1000000000000) and require minimum address of 0x10000 to reject garbage
    
    5. **Use maple tree's own metadata**: Replace undefined variables (isArangeNode,
       baseType, etc.) with proper mapleType constants
    
    Results: Successfully finds 80 valid VMAs at proper depth 2, correctly identifying
    tree structure as arange_64 internal nodes → leaf_64 nodes → VMA pointers.

    Fix PTE misinterpretation causing infinite page table walking
    
    Critical bug fix: PTEs (level 3) with type=3 were being misinterpreted as table
    descriptors pointing to non-existent level 4. ARM64 page tables have exactly 4 levels,
    and at PTE level, type=3 means a valid page mapping, not a table pointer.
    
    Changes:
    - Fix PTE handling: type=3 at level 3 means valid page, not table descriptor
    - Add explicit level check to prevent following PTEs as if they were tables
    - Replace spread operator with loop to prevent stack overflow on large arrays
    - Confirm kernel uses __GFP_ZERO (page tables are properly zeroed)
    
    This fixes the stack overflow errors and allows proper kernel memory analysis.
